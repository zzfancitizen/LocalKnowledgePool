## 一、Joule Work 是什么（一句话）

> Joule Work / Engagement Layer 是一个智能、统一、用户感知的**体验框架**，通过意图（intent）、上下文（context）和对话式 AI，把用户连接到 SAP 内外的各种能力。它把工作范式从 **app-centric（以应用为中心）** 转向 **intent-centric（以意图为中心）**，从被动聊天转向主动、组合式（compositional）、agent 协作的体验。

四大产品支柱：**Spaces**（生成式 UI 动态工作区）、**Conversations**（对话式 AI）、**Shell**（基础层与信息架构）、**Mobile**（原生移动）。此外有 **Jobs**（让 agentic 工作可观测/可验证/可治理）和 **Discover**（主动内容）。

**生产/里程碑：** Sapphire 26（2026-05，MVP）→ August 26（Discover + Jobs 首次可用）→ Nov 26（协作/多用户/scheduled jobs）。Jobs 生产目标 **2026-09-24**。

## 二、【重点】Developer 需要做哪些开发 —— 全局汇总

> 用户最关心的问题。以下按版块汇总各文件中提炼出的开发者工作项，细节见对应文件。

### A. Spaces 开发（最核心，详见 `03`）
1. **前端 spaces-ui**：React + TanStack Query + Zustand + UI5 Web Components；实现 **22 个 Card 组件 renderer** 与三种数据绑定（`$state` / `$template` / 隐式 field ref）。
2. **实时渲染**：rehydration 模式 + WebSocket 客户端（First Hydration + JSON Patch + echo-back）；客户端不轮询，响应 `CARD_DATA` / `ACTION` 生命周期事件。
3. **Spaces backend**：用 **SAP CAP** 建（CDS 模型 + OData v4 + WebSocket V2 协议 + 多租户 HDI 隔离 + action proxy）。四个后端服务：SMS（持久化）、SAS（maestro 编排 loop）、JOP（Joule 同步代理，Redis pub/sub）、Card Generation Service。
4. **SAS maestro loop 五阶段**：Planner / Workers（Dynamic Race）/ Evaluator / Safety Gate / Compositor，agent 保持无状态解耦。
5. **Card Generation Service**：LangChain skill agent，7 种 card type，QUAL 校验 + 重试，REST + MCP 双传输。
6. **数据链路**：Data Transformation 引擎（DuckDB 临时表）、Data Proxy（存 SQL view 不存数据 + Redis 缓存 + 双失效触发）。
7. **Enrichment**：UI Enrichment Proxy（确定性 `$select`/`$expand`）+ Joule cURL Function + Agent Connector→Business Connector→S/4 路由（后端连接 Option 0）；enriched response → board spec 的确定性转译。
8. **Feature flags** 管理（如 `ff_x_el_spaces_integration`）；补齐 **Joule 集成 gap**（突破 20 条限制/分页/聚合、结构化错误传播、capability discovery、扩大 write action 覆盖）。

### B. Agent 开发（让 agent 生成/驱动 space，详见 `04` 的 12 步清单）
1. 确定 space 类型（user-triggered vs system-triggered），理解组件链路各层职责。
2. **让 agent 可被发现**：ORD（system-version + system-instance）+ 两个 Agent Card + 接受 IAS app2app token。
3. **搭 capability 骨架**：`joule/a2a/capability.sapdas.yaml`（唯一 namespace、具体 description、`system_aliases`→BTP Destination），`scenarios/`、`functions/` 保持扁平。
4. **写 function**：构造 `refresh_handle`；结果严守契约——`raw_data.value` 永远是数组、无任何 UI artefact、只返回 data。
5. **按 surface 分支**：`condition: $transient.app_context.has('spaceId')` 决定响应形状。
6. **消灭三大隐形杀手**（slot filling / disambiguation / response-format）——每次测试前先跑 **Content Validator**。
7. **过 onboarding**：UMS/UCL/ORD/SPII 前置 → CMP-15763 AGW formation → SPII Wave 0/2 → Blueprint + canary → collector 注册到 active DA（`da_kgs4pub_el_agents`）+ `npm run validate/deploy`。
8. **按序测试**：Standalone Webclient → Content Validator → New EL Experience → ATIL API。
9. **system-triggered**：定义 user IAS token 策略、公网可达 callback、按 ATIL body 发请求、scenario 加 `input_prompt` slot。
10. **HITL space**：设计 Reporting vs Direction space（用户动作二元），域支持时后端实现 rollback。

### C. Jobs 开发（详见 `02`；注意 Backend Dev 岗位「待补充」）
1. **构建 Jobs Service（Sidecar / Option B）**：复用现有 scheduling service，新增 `showAsJob` flag、接收 agent 结果的 REST endpoint、job 元数据字段；不在执行热路径。
2. **Jobs 持久化 + 按需可解释性**：存 job 元数据/run/缓存输出/view config；用户打开详情时才惰性解释（不预处理）；长期存储探索 CLS。
3. **前端 UI 可观测性**（assistant-ui）：Unified Job View（EL-1243）、Job Detail（EL-1244）、四状态生命周期（EL-1246）、`STATE_DELTA`、组件目录版本化、多客户端渲染 fallback、SSE/XSS/CSRF 安全。
4. **AG-UI 协议适配**：ingest 边界采纳 `@ag-ui/core` + Zod 校验，`JOB_UPDATED`/`SET_RUN_ID` 映射为 `CUSTOM` 事件；publisher 契约 POST 到 `/api/agent/events`。
5. **Scheduler 集成**为通用 plugin/hook（消费 "job started" 事件做关联）。
6. **Telemetry 集成**：以 CLS 为存储后端；定义 `sap.jobs.*` OTel 语义约定；消费 CIG 风格业务级 OTEL log。
7. **HITL 决策 UI**（不建模 HITL 本体）：呈现 Needs Attention + typed decision surface（approve/modify/escalate/reject + rationale），经 callback 回传 agent。

### D. 平台级硬性技术约束（所有开发者，详见 `01` 与 `05`）
1. **可观测性**：必须用 **OpenTelemetry** 端到端 tracing（UI→服务→Joule Orchestrator→agents）；P1 MTTRC <5 分钟、100% 覆盖；React 无专用库需手动埋点；敏感/DPP 数据不得记录并需 data masking；应用须在 URL 中管理状态以支持 deep linking。
2. **性能 SLA**：conversation <1s、space 生成 <3s（P90）、Joule Orchestrator 编排 <500ms、KG/AutoSQL 查询成功率 >85%；PERF-01 量化门槛（列表 3s、生成 1s 反馈/6s 首卡/30s 全量）——当前被「无测试 landscape」阻塞。
3. **安全/身份**：100% principal propagation + 联邦身份（S/4HANA Cloud + SuccessFactors）；agent 授权过 SOC2；带权限边界的 agent 授权。
4. **内容/导航**：走 **CDM + IBN**——产品需成为 CDM content provider、实现 SPII、参与 formation；URL 模板基于 RFC6570（不必 hash 路由）。
5. **授权两层模型**：设计时 CDM 定义角色要求 + 运行时 SCI 提供用户角色；LoB 需将角色复制到 IdDS。
6. **Task Center 集成**：Provider 必须 SAP Managed、支持 IAS App2App 主体传播、每 SCI 租户单例。
7. **移动端**：`/joule` 代理路由无需 token 交换；BKG/KG 只读且返回技术码（须经 tools-bridge UI enrichment 解析码→标签）；数据+动作应一次响应返回、action 执行需确定性路径（无 LLM）。

### E. 关键依赖（外部系统，来自 OKR）
- **Joule Orchestrator**（编排 <500ms）、**Business Content Service / CDM Replication API**、**SAP Task Center**（每 SCI 单例）、**ANS**（formation provisioning + 深链接）、**Knowledge Graph + AutoSQL**（查询成功率 >85%）。

## 三、重要提醒（就绪度）

- **Discover 与 Jobs（Assistant）** 明确**不在 Sapphire 2026 生产化范围**，首次可用为 **August 26**。若有相关用例，现在应记录需求、参与 EAC，暂用 system-generated spaces PoC 做原型。
- **Spaces 与 Develop（低代码）当前是独立产品**，集成点在 August 26 / Nov 26。
- **多用户 Spaces** 在 Nov 26 才有；Sapphire 26 仅单用户，需用 ANS 通知交接 + Task Center 协调。
- **Space 布局不确定**（compositional，相同 prompt 可能不同布局）；要可控布局须走 **agent 显式 spec / system-generated space** 路线 + Content Validator 校验。
